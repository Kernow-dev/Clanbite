# Clanbite Agent Guidance

## Role And Mindset
- Act as a professional WordPress developer with a passion for gaming communities and esports products.
- Prioritize extensibility, backward compatibility, and predictable upgrade paths.
- Favor maintainable architecture over short-term hacks.
- Assume **third-party developers do not have full context** on the codebase: document public APIs, hooks, and non-obvious behavior in PHPDoc and keep this file aligned with real extension points.

## Engineering Standards
- **Naming prefix.** Every identifier uses `clanbite` (`clanbite_` for PHP, options, meta keys, post types, tables and extension slugs; `clanbite-` for CSS classes, handles and `data-clanbite-*` attributes). The old `cp_` / `cp-` prefix is retired: do not reintroduce it. Names that are stored in the database changed once in `Maintenance::run_2()` (`inc/clanbite-cpt-identifier-migration.php`, then `inc/clanbite-legacy-prefix-migration.php`). **Every data change on upgrade goes in `Kernowdev\Clanbite\Maintenance` as a new `run_N()` step with `Main::MAINTENANCE_VERSION` raised to N**, not on its own hook. A post type's query variable is its own name, so never reuse a post type name as a URL argument (the player Events page uses `clanbite_event_view`).
- Follow the latest WordPress Coding Standards (WPCS), modern PHP practices, and secure WP APIs.
- Use strict sanitization/escaping, capability checks, nonce verification, and i18n functions.

### Formatting tooling (keep file types separate)
- **PHP** is checked and fixed with PHPCS/PHPCBF using each plugin's `phpcs.xml.dist` (WordPress-Core + WordPress-Docs + Security). Every ruleset is PHP-only (`<arg name="extensions" value="php"/>`) and excludes generated `build/`. **Never run `phpcbf` over JS/CSS**: PHPCS' default extensions include them, and its PHP alignment/operator rules corrupt JSX and template literals (`< / span >`, `${ base } / path`, `a ? .b`).
- **JS** uses `npx wp-scripts lint-js --fix --ignore-pattern 'assets/dist/**'`; **CSS/SCSS** uses `npx wp-scripts lint-style --fix`. Note `lint-style --fix <file>` ignores the path and fixes the whole project, so commit or snapshot first.
- Use the globally installed `phpcs` (`~/.composer/vendor/bin`); the vendored copies in the companion plugins can print nothing and look falsely clean.
- After any bulk fix, verify behavior is unchanged: rebuild and compare compiled CSS, parse every JS file (Babel with the JSX plugin), `php -l` every PHP file (not only changed ones), and compare PHP token streams ignoring whitespace and comments.

## WordPress.org Plugin Check And PHPCS (Agent Checklist)

These items recur in **Plugin Check** / **PHPCS** runs. Prefer fixing **errors** before **warnings**; avoid drive-by warning sweeps unless the maintainer asks.

### Direct file access (`ABSPATH`)
- **Every** PHP file that ships with the plugin should include `defined( 'ABSPATH' ) || exit;` (or equivalent) so the file cannot be executed directly.
- **Namespaced files** (`namespace …;`): put the guard on the line **immediately after** the `namespace` statement. Only `declare()` may appear before `namespace` in PHP; do **not** place the guard before `namespace`.
- **Procedural files** (no namespace): put the guard right after `<?php`, before `use` imports or other logic (e.g. `shortcut-function.php`, `templates/**/*.php`, `languages/index.php`).
- **Block server markup**: add the guard in **`src/blocks/**/render.php`** (source of truth). Webpack copies into **`build/`**; editing only `build/` is lost on the next `npm run build`.
- **`build/**/blocks-manifest.php`**: treat like other shipped PHP; include the guard.

### Generated `*.asset.php` (webpack / `@wordpress/scripts`)
- Default output is often a **single line**: `<?php return array( … );`. If Plugin Check requires a direct-access guard, the file must be **multi-line** so the guard runs **before** `return`:
  - `<?php` → blank line → `defined( 'ABSPATH' ) || exit;` → blank line → `return array( … );`
- **Do not** append the guard **after** a one-line `return` (it never executes).
- **`npm run build`** may **regenerate** `build/**/index.asset.php` (and similar). If checks regress after a build, restore this shape, adjust the build pipeline, or exclude generated assets per project policy—do not assume a one-time manual edit sticks.

### Plugin header: `Domain Path`
- **`Domain Path`** must use a **leading slash** per WordPress / Plugin Check (e.g. `/languages`) and match a **real** folder under the plugin root (`languages/`). Keep a minimal `languages/index.php` with a direct-access guard so the directory is valid even before `.mo` files exist.

### Shipped assets: file names
- Under **`assets/`** (and anywhere in the distributable zip), use **no spaces** and **no odd characters** in file and folder names (Plugin Check `badly_named_files`). Prefer lowercase `a-z0-9._-`.
- **`node_modules/`** may contain third-party files with bad names (e.g. copied flag packs). Release artifacts should **exclude** `node_modules` (see **`.distignore`**). When running Plugin Check locally on a dev tree, **exclude `node_modules`** from the scan scope if the tool allows—do not rename files inside dependencies.

### Filesystem moves (uploads / temp files)
- Avoid bare PHP **`rename()`** for paths WordPress owns; use **`WP_Filesystem`** and **`$wp_filesystem->move()`** after `WP_Filesystem()` is initialized (satisfies `WordPress.WP.AlternativeFunctions.rename_rename`).

### Database (`$wpdb`)
- Favor **`$wpdb->prepare()`** for all dynamic **values**. Table names are not placeholders: build them from trusted sources (e.g. `$wpdb->prefix` + known suffix) and document why; use a **narrow `phpcs:ignore`** with a one-line rationale when sniffs flag “NotPrepared” for identifier-safe SQL.
- **`LIMIT` / `OFFSET`**: use integer casting or placeholders in a way your PHPCS rules accept; avoid passing unchecked user strings into raw SQL fragments.

### Admin / developer diagnostics (`_doing_it_wrong`, loader validation)
- Messages passed to **`_doing_it_wrong()`** (and similar core APIs) are **developer-facing**, not theme output. **Do not** blindly wrap them in `esc_html()` if that breaks translation placeholders.
- If **`WordPress.Security.EscapeOutput.OutputNotEscaped`** fires on those calls, use a **tight `phpcs:disable` / `phpcs:enable`** around the specific block, or an inline ignore on the line, with a short comment.

### Exceptions with translated strings
- **`InvalidArgumentException`** (and similar) with `__( … )` may trigger **`ExceptionNotEscaped`**. Prefer a documented **`phpcs:ignore WordPress.Security.EscapeOutput.ExceptionNotEscaped`** on the `throw` line over removing translations.

### Expectations: warnings you may not “fix” in one pass
- **Block `render.php`** and classic templates often trigger **`PrefixAllGlobals`** for `$block`, `$attributes`, etc.; that is normal for WordPress templates unless the project adopts file-level exclusions.
- **`load_plugin_textdomain()`** may be flagged as discouraged for WordPress.org-hosted plugins; follow product policy (keep for non.org installs or drop when fully on language packs only).
- Do **not** rename WordPress core globals (e.g. `$_wp_current_template_id`) to satisfy prefix rules.

## Documentation Standard (Required For Third-Party Extensibility)

### PHPDoc (PHP)
- **Every** `public` and `protected` class method: short summary, `@param` for each parameter, and `@return` where applicable.
- **Interfaces**: document each method the same way.
- **Procedural helpers** (`clanbite_*()` in `functions.php` files): summary, `@param`, `@return`.
- **Hooks** (`apply_filters` / `do_action`, and `wp.hooks` calls in JS): inline block immediately above the call with a summary, then `@param` for every argument (type and meaning). That block is the **single source of truth**: `HOOKS.md` in each plugin is generated from it (`composer docs:hooks`; `composer docs:hooks:check` fails when it is stale). Never hand-edit `HOOKS.md`.
- **Classes**: file-level `@package clanbite` and a class summary describing responsibility and how extension authors should use it.

### `@since` tags
- Do **not** add `@since` while the plugin version is **1.0.0** (initial public API is treated as the baseline).
- After the plugin moves **beyond 1.0.0**, add `@since x.y.z` to **every new** public API surface (methods, functions, hooks, filter/action names) introduced in that release, and preserve backward compatibility for existing integrators.

### README And This File
- When adding or changing hooks, extension registration, or data-store contracts, update **`README.md`** (developer-facing sections) in the same change.
- Update **`AGENTS.md`** when you introduce new **categories** of extension points (e.g. a new data-store interface) or change the extension lifecycle.

## Extension Architecture (For Third-Party Authors)

### `requires` vs `parent_slug` (do not conflate)
- **`requires`**: Other extension slugs that **must be installed and enabled** before this one can run. Use this for hard dependencies (e.g. Matches **requires** Teams). This does **not** imply a parent/child relationship in the UI or in data modeling.
- **`parent_slug`**: Use **only** when this extension is intentionally a **sub-extension** of another (same product family, settings grouped under the parent in the unified admin, shared lifecycle semantics). Leave **`parent_slug` empty** for a normal top-level extension even if it lists dependencies in `requires`.

### Lifecycle
1. **Construct** your class extending `Kernowdev\Clanbite\Extensions\Skeleton` with a unique slug (lowercase, `a-z0-9_-`), name, version `x.y.z`, optional `parent_slug` (only for true sub-extensions), and `requires` slugs (hard dependencies).
2. **Register** on `clanbite_registered_extensions` (third-party) or `clanbite_official_registered_extensions` (first-party whitelist only — do not use for community extensions).
3. **Install**: site admin enables the extension in **Clanbite → Extensions**; stored in `clanbite_installed_extensions` (per-site option, or site option when saving from network admin).
4. **Boot**: `Loader::setup_extensions()` calls `can_install()`, optionally `run_updater()`, then `run()` for each installed extension.
5. **Data**: optional JSON-like blob per extension via `Skeleton::get_data()` / `set_data()` / `delete_data()` backed by `Extension_Data_Store` (filterable).

### Hook Reference (Core Extension Flow)
This list is a curated overview of the main extension flow. The **complete, generated reference** (every hook, with arguments and source file) is `HOOKS.md` in each plugin: core, Forums, Social Kit, Points and Ranks.

**Filters**
- `clanbite_registered_extensions` — Register community / third-party extensions: `(array $slug => Skeleton)`.
- `clanbite_official_registered_extensions` — First-party only; must match whitelist in `Loader::get_official_extensions()`. Whitelist entries may point at classes loaded by **bundled** code or by a **separate first-party plugin** (same validation path; **Core** badge still comes only from `clanbite_core_bundled_extension_slugs`).
- `clanbite_extension_data_store` — Replace `Extension_Data_Store` for a given extension: args `( $data_store, $slug, Skeleton $extension )`.
- `clanbite_extension_{slug}_block_directories` / `clanbite_extension_block_directories` — Block build paths before `register_block_type_from_metadata` when using `Skeleton::register_extension_blocks()` (not used by first-party metadata-collection registration).
- `clanbite_extension_{slug}_templates` / `clanbite_extension_templates` — FSE template definitions for `register_block_template`.
- `clanbite_player_settings_frontend_config` — Filter the array passed to `wp_localize_script` as `CLANBITEPLAYERSETTINGS` (keys: `ajax_url`, `nonce`, `rest_url`, `rest_nonce`, and on the player settings screen `settings_url_base`, `settings_initial_nav`, `settings_initial_panel`). Used by the player-settings block for REST-backed extension UI and deep-link routing; see README **Player settings (front-end): plugin actions**.
- `clanbite_should_enqueue_player_settings_frontend_assets` — Gate whether `CLANBITEPLAYERSETTINGS` is printed on a front request: `(bool $enqueue)` after core heuristics (player settings route, logged-in author profile, singular posts with the player-settings block). Return true to force enqueue when custom templates need the payload.
- `clanbite_can_install_{slug}_extension` — Extra install gates: `(bool $can_install, Skeleton $extension)`.
- `clanbite_validate_installed_extensions` — After admin saves extension list: `( $new_installed, $requested, $available_extensions )`.
- `clanbite_visibility_container_should_show` — Whether to render **Visibility container** inner blocks for the current visitor: `(bool $visible, array $attributes, \WP_Block|null $block)`.
- `clanbite_visibility_container_editor_script_handle` — Override the script handle used to pass role labels into the visibility-container block editor: `(string $handle)` (default: registered `editorScript` for `clanbite/visibility-container`).
- `clanbite_required_extension_slugs` — Slugs that cannot be disabled (default `clanbite_players` only): `(array $slugs)`.
- `clanbite_core_bundled_extension_slugs` — Slugs shipped inside the main Clanbite plugin (admin **Core** badge); excludes separate add-on plugins: `(array $slugs)`.
- `clanbite_install_notifications_extension_by_default` — If true (default), the loader runs a **one-time** migration that adds `clanbite_notifications` to installed extensions when missing; set false before first boot to skip: `(bool $enable)`.

- `clanbite_notifications_extension_active` — Whether in-site notifications are considered available (installed `clanbite_notifications`): `(bool $active)`. Theme and third-party code should use `clanbite_notifications_extension_active()` or handle `WP_Error` from `clanbite_notify()` (code `notifications_inactive`).
- `clanbite_events_extension_active` — Whether scheduled events (`clanbite_event`, RSVP REST, event blocks) are available (installed `clanbite_events`): `(bool $active)`. Use `clanbite_events_extension_active()` before assuming event APIs exist.

- `clanbite_players_directory_per_page` — User-query page size on the players directory shortcode: `(int $per_page)`.

## Team permissions
Team managers get `edit_post` on their own team, which WordPress treats as far more than the manage screen offers. Keep these limits (all in the Teams extension) and run `php tests/php/team-permissions.php` after changing team permissions, roster saving or team ranks:
- Restricted users (not a teams site admin, no `edit_others_posts`) cannot change the columns in `get_protected_team_post_fields()` (REST error plus a `wp_insert_post_data` backstop), and lose `edit_post` while the team's front-end editing is off.
- The roster roles meta is never writable through `*_post_meta` capabilities; save it with `persist_team_roles_map()`.
- A form or route that lets a team manager save a roster must not add people who have not accepted an invitation. `persist_team_roles_map()` itself does not check this.
- Send invitations through `Team_Invites::invite()` (it applies every rule); `send_team_invite()` only delivers one. Never create a second invite route.
- A registered boolean meta with a `true` default is stored as `''` when saved false: test `metadata_exists()` before treating empty as "yes".
- Anything stored per team and per player (such as team ranks) must check current membership and clear on `clanbite_team_roster_updated`.

## Privacy of post types (read before adding one)
WordPress lets **anyone read a published post of any `show_in_rest` post type**, even with `public => false`, and a `public` post type also gets a page, archive, feed, embed, sitemap and search results. A visibility setting enforced only on Clanbite's routes and blocks is not enforced. For every post type with its own rules:
- Guard `/wp/v2/{rest_base}` (filter `rest_dispatch_request`, reading `$request->get_route()` case-insensitively; the third argument is the route **pattern**), or give the type its own capabilities (as coupons do).
- For public types, also cover collections and `wp/v2/search` (remember `post__not_in` is ignored when `post__in` is set), front-end pages, oEmbed and sitemaps (see `Match_Privacy`).
- A group's join setting caps its content: check `clanbite_groups_viewer_can_see_content()`.
- Test with real requests (`rest_do_request()`), not by calling the guard with made-up arguments: `php tests/php/content-privacy.php`.

## Shared components (one implementation, many extensions)
- **Never build a second copy of a component.** A feature that more than one extension shows (avatars, buttons, popups/toasts, reactions, @mentions, player cards, messages) has exactly one home, and the other extensions call it. Third parties then hook into one place.
- **Homes:** core Clanbite owns what every site needs (avatars `clanbite_render_avatar()`, buttons, toasts, messages registry, profile subpages). A companion owns a feature other extensions may enhance: **Social Kit owns reactions** (`clanbite_social_kit_register_reactable()`, `Reactions::toggle()`, one REST route, `clanbite_social_kit_can_react`, `clanbite_social_kit_object_reaction_toggled`) and @mentions. An extension that shows such a feature when its owner is installed (Forums reactions need Social Kit) registers with the owner and shows nothing otherwise; it does not fall back to its own implementation.
- **The registry is how consumers reach a shared component:** `clanbite_register_component()` on `clanbite_register_components`, then `clanbite_has_component()` / `clanbite_render_component()` / `clanbite_enqueue_component()` (see `inc/components.php`; browser: `window.clanbite.components`). Do not add `function_exists()` checks on another plugin's helpers for a shared component; register it, declare `requires`, and consume it through the registry. Companions that must run next to an older core wrap the call with a fallback (see `clanbite_forums_has_component()`).
- **Surface classes.** A shared component adds where it is shown as a CSS class (`is-{surface}` / `is-{context}`: `is-forums`, `is-feed`, `is-social-feed`), so each surface is styled independently and a theme can target one place. New shared components must do the same.
- **Context is part of the contract.** Shared component calls carry where they are shown and who is looking (avatars: `context`, `viewer_id`, `is_viewer`, `object_type`, `object_id`, `extension`, `context_data`), so one filter can vary behaviour per surface.
- **Gate with global function names** (`function_exists( 'clanbite_social_kit_register_reactable' )`), never class existence or namespaced functions.

## Backward-compatibility promise (binding)
Within a major version nothing documented is removed or changes meaning: PHP functions/classes with PHPDoc, hooks and their arguments, `clanbite/v1` REST routes, block names and attributes, template-part names, option keys and data formats; database changes are additive only. Deprecate in a minor (`_deprecated_function()` / `_deprecated_hook()` with a replacement) and remove only in the next major. Add-on release headers declare compatibility: `Requires Clanbite: ^X.Y.Z` is mandatory (CI and the update server refuse a release without it), `Requires Clanbite Add-ons: slug constraint, …` is optional. When a depended-on add-on needs a breaking major, ship a bridge release of the dependent one first.

## Add-on guard (`Compat\Compat_Monitor`)
Core deactivates (silently) any plugin that declares `Requires Clanbite` and cannot run on the installed Clanbite, and re-enables it when it can. Rules: judge against the version **on disk** after an update (`upgrader_process_complete` runs inside the old code); never run an incompatible plugin's own deactivation hooks; re-enable only in admin or cron; leave plugins without the header alone (except first-party add-ons, which default to `^1.0.0`); keep `Version_Constraint` identical to the server's copy. Changing what counts as incompatible is a behaviour change for every site: add a test with throwaway plugins and never run a simulated-version sweep against a site's real active plugins. One request at a time sweeps: `sweep()` takes a database lock (`clanbite_addon_guard.lock`), re-reads the options once it holds it, and `maybe_sweep()` skips instead of waiting. Keep new entry points behind that lock; `php tests/php/addon-guard-concurrency.php` races real processes against throwaway plugins.

## Blocks (Gutenberg)
- **Block inserter icons:** Per-block modules in `src/blocks/shared/block-icons/icons/{slug}.js` (Heroicons 24 solid via `@heroicons/react`). Each block’s `index.js` imports `clanbiteBlockIcon` from its slug file and passes `icon: clanbiteBlockIcon()` to `registerBlockType( metadata, … )`. Regenerate mapping with `node scripts/generate-block-icons.mjs`; then `npm run build:blocks`.
- **Do not** register Clanbite blocks with `register_block_type()` in PHP (no PHP-only `render_callback` / attribute definitions) **unless the maintainer explicitly asks for that approach**.
- **Buttons:** every action button is `wp-element-button clanbite-button clanbite-button--{primary|ghost|danger}` (wrapper form: `wp-block-button` + `wp-block-button__link`), so theme.json styles it. The shared contract is `src/assets/css/clanbite-buttons.css`, registered as style handle `clanbite-buttons`; add it to the block's `block.json` `style` array (companions reuse the core handle) or `wp_enqueue_style()` it from template output. Never set background, colour, border, padding, radius or font on a button class in block SCSS; position only. Fixed light/dark colours (`#fff`, `#1d2327`, `rgba(0,0,0,.x)`) are bugs on dark themes: use the theme-adaptive tokens from the `clanbite-tokens` handle (`--clanbite-surface`, `-on-surface`, `-surface-alt`, `-border`, `-muted`, `-accent`, `-danger`, `-success`) always with a standalone `var(--clanbite-x, fallback)`, or `currentcolor`/`color-mix()`. Button defaults are zero-specificity (`:where()`), so the plugin looks finished on any theme and any theme rule still wins. See **`DESIGN-SYSTEM.md`**.
- **Unified class naming system:** All Clanbite blocks follow a consistent BEM-based naming convention documented in **`DESIGN-SYSTEM.md`**. Buttons use WordPress core classes (`wp-block-button`, `wp-element-button`) for theme.json compatibility plus Clanbite variants (`clanbite-button`, `clanbite-button--primary`). Avatars, covers, and other components use unified base classes (e.g., `clanbite-avatar`, `clanbite-cover`) with type modifiers (e.g., `clanbite-avatar--player`, `clanbite-cover--team`). Shared styles are in **`src/blocks/shared/styles/`** (`_buttons.scss`, `_avatars.scss`, `_covers.scss`) and imported by individual block styles. Backward compatibility is maintained for legacy class names via SCSS `@extend`.
- Blocks are **real JS blocks**: `block.json` with `editorScript` (and optional `style` / `editorStyle`), **built** with `@wordpress/scripts` from **`src/blocks/`** into the plugin root **`build/`** (matches / players / teams subtrees). Register with **`Skeleton::register_extension_block_types_from_metadata_collection( 'build/…' )`** (WordPress 6.8+ metadata collection API; fallbacks in `Skeleton` for older core). Use **`Skeleton::register_extension_blocks()`** only for extra third-party-style block directories.
- **Server output** for dynamic blocks belongs in **`render.php`** next to the block source under `src/blocks/…`, copied into `build/` by `--webpack-copy-php`, not in ad-hoc PHP callbacks in the extension class.
- **`get_block_wrapper_attributes()`** returns an already-escaped attribute string: echo it directly (with a `phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped` and a short rationale). Do not pass it through `wp_kses_post()` / `wp_kses_data()` (risk to `data-wp-*` directives). Pass the **`$block`** instance as the second argument when available.
- After changing block sources, run **`npm run build:production`** (or **`npm run plugin-zip`** for a release zip).

### Build pipeline: everything served is built by `@wordpress/scripts`
- **Never enqueue a hand-written file.** Every script and stylesheet a plugin serves (blocks, shared components, admin screens, add-on assets) is a webpack entry built with `wp-scripts`, so production output is minified and gets an `*.asset.php` (dependencies and version). Blocks and their view modules build from `src/blocks/` into `build/` (`--experimental-modules` for `viewScriptModule`); every other script and stylesheet lives in `src/assets/` and is built by the plugin's `webpack.config.cjs` into `assets/dist/` with the same relative path. PHP registers the `assets/dist/` path; the sources under `src/assets/` are never loaded. `assets/dist/` and `build/` are generated and not committed.
- A script and its stylesheet share one entry (an array), so they keep one name. The build's `wrap-asset-php-guard.mjs` adds the direct-access guard to generated PHP and removes the empty script webpack emits for a CSS-only entry.
- **A script module that belongs to no block** (such as the team manage screen's `src/blocks/teams/team-manage-form/view.js`) is **not** picked up by the block build. Add it as an entry in `webpack.modules.config.cjs` (run by `build:modules`, part of `build:production`), and check that every `build/` path PHP enqueues exists after a build.
- **One exception:** `assets/js/clanbite-interactivity-bootstrap.js` is a single `import '@wordpress/interactivity';` line registered as a script module so the import map has the dependency. It has nothing to minify and is not built.
- Do not add copy scripts that move source files into `build/`, and do not link CSS between plugins with `@import` paths outside `src/`.

## Cross-plugin uniformity and WordPress 7.0 readiness
- **Headers:** every plugin declares `Requires at least: 6.9`, `Requires PHP: 8.2` (core, the Add-on Manager, Forums, Social Kit, Points, Ranks, Shop and Support Desk: do not use PHP 8.3 or 8.4 features in any plugin), `Requires Plugins: clanbite` (companions only; bare slug), `Text Domain` equal to the folder name, and `Domain Path: /languages`. `readme.txt` (`Requires at least`, `Stable tag`) and `package.json` `version` must match the main-file header. **`Tested up to` lives only in `readme.txt`** (currently 7.1): Plugin Check errors when it is also in the PHP header.
- **Translations:** each plugin registers one `load_textdomain()` method on `plugins_loaded` priority 1 that calls `load_plugin_textdomain()` (WordPress 6.7+ logs a notice when a string is translated before its domain loads). Do not hand-roll `.mo` lookups.
- **Editor APIs:** use `wp.editor` / `@wordpress/editor` for `PluginDocumentSettingPanel` (the `wp.editPost` slot is deprecated and the `wp-edit-post` script dependency must not be added). Every `@wordpress/components` form control sets `__nextHasNoMarginBottom` and, for text-like controls, `__next40pxDefaultSize` (WordPress 7.0 still warns without them). `__experimental*` imports are acceptable only while WordPress exports nothing else under that name.
- **Deprecations:** run `phpcs` with `WordPress.WP.DeprecatedFunctions` / `DeprecatedClasses` / `DeprecatedParameters` at `minimum_supported_wp_version` 6.9 before release.

## Interactivity API rules (server-rendered initial state)
- WordPress evaluates `data-wp-bind--*`, `data-wp-class--*`, `data-wp-text` and `data-wp-each` **on the server** for blocks with `supports.interactivity`, and it only knows PHP `state` (`wp_interactivity_state()`, including derived-state closures) and `data-wp-context`. A binding to `callbacks.*`, a JS-only `state` getter, or a path with call syntax (`state.foo()`) resolves to `null` there: a plain `hidden` binding then **removes** the `hidden` PHP rendered, so popups flash open until hydration.
- Bind visibility to `context.*` or to `state.*` that PHP also defines. For derived values, define a getter in `state` in the view script **and** a closure of the same name in PHP (popups and menus start closed, so the initial value is `true`). Never bind a negated function; use a getter.
- Paths are property paths: write `state.canGoNext`, never `state.canGoNext()`.
- Re-assert `[hidden]` in block CSS (an author `display` value beats the browser's `[hidden]` rule); core ships it in `src/blocks/shared/styles/_hidden.scss`.
- **Plugin PHP templates need an import map.** A template that calls `get_header()` and renders blocks afterwards (group pages, classic-theme fallbacks) prints the import map before the blocks' view modules exist, so the browser cannot resolve `@wordpress/interactivity`. Core's `enqueue_interactivity_for_plugin_templates()` (`template_include`, priority 9999; on block themes it also adds the title and viewport tags such pages would otherwise lack) enqueues the empty module `clanbite-interactivity-bootstrap` early for any template inside a `clanbite*` plugin folder; keep such templates under their plugin's `templates/` folder, or enqueue that module yourself. Pass only a real theme template to `locate_block_template()` (see `clanbite_locate_block_or_plugin_template()`).
- **Popups float above content automatically.** Any element marked `data-clanbite-popup` is promoted to the browser's top layer (Popover API) while it is open, keeps the spot its own CSS gave it and follows scrolling, so a post, card or avatar can never cover or clip it. Do not fight stacking with `z-index`; opt a popup out with `data-clanbite-float="off"`.
- Every popup fires `clanbite.popup.toggled` (`{ name, open, root }`) and honours the `clanbite.popup.shouldOpen` filter; enqueue the `popups` component (`clanbite_enqueue_component( 'popups' )`), call `window.clanbite.popups.announce( name, open, root )` from a `callbacks.announcePopup` watch (`data-wp-watch="callbacks.announcePopup"` on the root) and gate opening with `window.clanbite.popups.allowOpen( name, root )`. Popovers driven by a `hidden` binding instead carry `data-clanbite-popup="name"` (the client announces them for every open and close path) and their open actions call `allowOpen()`. Never copy these helpers into a block.
- Any `file:` asset declared in `block.json` must be produced by the build (import `style.scss` / `editor.scss` from `index.js`).

## Admin Extension Interface
- **Where a setting lives (one rule).** A setting goes on the tab of the extension that owns the feature, including the profile tabs, popups and defaults that feature adds: Events owns its three profile tabs, Matches its team tab, Notifications its player tab and the shared popups, Ranks its status updates and team ranks. Do not put a feature's switch on another extension's tab (and do not inject it there from an add-on with a section filter), and never keep two switches for one behaviour. When you move a setting, carry the saved value over once (a migration flagged by an option) and keep a read fallback to the old location; do not delete the old key.
- **Sub-navigation on any tab:** third parties add views to a tab's sub-menu with `clanbite_register_admin_sub_tab( $tab_id, array( 'id', 'label', 'slotId', 'capability', 'priority' ) )` (wrapper for the `clanbite_admin_rest_sub_tabs` filter, `inc/admin/functions.php`). It works for every tab type. Core validates and orders entries in `clanbite_normalize_admin_sub_tabs()` and renders an empty integration slot for the active `?view=`; the plugin's own script mounts into it on `clanbite:admin-integration-mount` and must do so idempotently. First-party reference: Ranks → **Manage members**. Do not give a companion its own top-level or submenu page when the content belongs to an extension tab.
- The unified **Clanbite** React settings screen keeps the active tab in the query string: `admin.php?page=clanbite&tab=<tabId>` (e.g. `general`, `extensions`, `ext-clanbite_teams`). Implementations should update `?tab=` when the user switches tabs and honor it on load so refresh and shared links reopen the same tab.
- Treat the extensions screen as critical UX: clear statuses, dependency visibility, and safe install toggles.
- Do not allow enabling extensions with unmet requirements.
- Keep admin actions idempotent and validated server-side.

## Documentation Workflow
- Keep `README.md` current whenever architecture, extension APIs, hooks, or setup steps change.
- Document new hooks and extension points in the README at the same time as code changes.
- When touching a public API surface, update PHPDoc in the same PR/commit so IDE hints and static analysis stay accurate.
- After adding or changing a hook, run `composer docs:hooks` (and commit `HOOKS.md`); CI/pre-release should run `composer docs:hooks:check`.
- **Companion plugins must expose their public helpers under global names.** A function defined inside a namespace is invisible to `function_exists( 'clanbite_x' )`, so a namespaced `functions.php` needs an un-namespaced `inc/functions-global.php` of guarded aliases (see Points and Ranks). Cross-plugin integrations must gate on those global names, and any "demo" or placeholder rendering belongs behind an opt-in filter, never as the fallback.
